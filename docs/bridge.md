# Мост через чат

Контракт обмена с Claude без API (устав M4, решения 1 и 2). Появился в M4.1.
Код: `backend/app/pipeline/bridge/` (`prompts.py` — шаблоны и рендер, `extract.py` — JSON из ответа, `runs.py` —
журнал, `errors.py` — ошибка ответа), роутер `backend/app/api/bridge.py`, миграция `006_bridge.sql`. Шаблоны —
`backend/app/prompts/<id>.md`.

## Задача моста

Задача моста — промпт из шаблона плюс контекст, который собирает код. Пользователь копирует промпт в claude.ai, чат
отвечает, ответ вставляется в приложение. Бэкенд достаёт из ответа ровно один JSON, проверяет его схемой задачи и
применяет. Задачи (`BridgeTask`):

| `task` | Что приходит | Этап |
|---|---|---|
| `plan` | `director.json` частями по `plan.shots_per_part` кадров | M4.2 |
| `ideas` | идеи для бэклога | M4.8 |
| `reference` | разбор референса: сегменты, приёмы, факты | M4.10 |

Приложение не открывает claude.ai, не читает буфер обмена и не обращается к подписке из кода (`CLAUDE.md`, «Чего не
делать»). Копирование — по клику, вставка — руками. Будущий API-этап возьмёт те же шаблоны: промпт не знает, как его
доставят.

## Шаблоны

Файл `backend/app/prompts/<id>.md`: front-matter между строками `---`, дальше текст промпта на английском.

```markdown
---
id: plan
version: 1
task: plan
model_hint: opus
---
You are writing part {{part}} of {{parts_total}} of a director plan for the channel {{channel}}.

Brief:
{{brief_json}}
```

| Поле | Тип | Правило |
|---|---|---|
| `id` | `^[a-z][a-z0-9_-]*$` | равен имени файла без `.md`, отсюда уникальность |
| `version` | целое ≥ 1 | меняется текст шаблона — растёт `version` |
| `task` | `plan \| ideas \| reference` | задача моста |
| `model_hint` | строка | для какой модели писался текст (`opus`, `sonnet`); не ID модели (принцип 5) |

Лишнее поле — ошибка. Шаблоны проверяются при старте (`load_templates` в `create_app`). Битый front-matter, `id`
мимо имени файла или непонятная подстановка (`{{ idea }}` с пробелами) дают `ConfigError`, и бэкенд не стартует.
Каталога ещё нет — шаблонов ноль, это не ошибка.

**Версия промпта.** Любая правка текста, даже одной запятой, поднимает `version`. Хэш в журнале покажет, что текст
другой, а версия скажет, какой именно. Старые версии лежат в истории git.

### Рендер

`PromptLibrary.render(id, context) → RenderedPrompt {text, prompt_id, version, sha256}`, где `sha256` — hex
SHA-256 текста в UTF-8.

- Подстановка — `{{name}}`: строчные латинские буквы, цифры, `_`, без пробелов.
- Каждое имя из шаблона должно прийти в контексте, и каждый ключ контекста должен быть в шаблоне. Иначе
  `PromptRenderError` с именами ключей: «Шаблон «plan»: нет значений для {{brief_json}}; лишние ключи контекста: angle.»
  Пустая строка вместо пропуска не подставляется.
- Значения — строки, подставляются как есть, за один проход: `{{…}}` внутри значения не раскрывается повторно.
- JSON-фрагменты контекста сериализует код: `json_block(value)` = `json.dumps(value, indent=2, ensure_ascii=False)`.
- Рендер детерминирован: тот же шаблон и тот же контекст дают тот же текст и хэш.

## Разбор ответа

`extract_json(text) → dict` или `BridgeAnswerError(message, hint)`. Порядок:

1. **Блоки кода.** Берутся блоки ```` ```json ```` (язык без учёта регистра). Если их нет — блоки ```` ``` ```` без
   языка, начинающиеся с `{`. Блоки других языков (```` ```python ````) пропускаются. Два подходящих блока и больше —
   ошибка. Блок без закрывающей ```` ``` ```` идёт до конца ответа.
2. **Нет блока** — первый `{` в тексте и его пара. Скобки внутри строк и экранированные кавычки учитываются, так
   что проза вокруг допустима.
3. **Скобки не закрылись** до конца блока или ответа — ответ обрезан.
4. **Разбор** — стандартный `json`. Позиция ошибки пересчитывается в строку и столбец исходного ответа (как его
   видит пользователь), а не вырезанного куска. Внутри блока весь его текст — один JSON: второй объект в том же блоке
   даёт ошибку «лишний текст».
5. **Результат** — только объект. Список, строка или `NaN`/`Infinity` — ошибка.

Ничего не «чинится»: висячая запятая, одинарные кавычки, комментарии, перенос строки внутри строки — это ошибка, а
не догадка. Неверный ответ лучше переспросить у чата, чем применить не то.

| Ответ | Результат |
|---|---|
| `Here is part 1.` + блок ```` ```json {…} ```` + `Let me know…` | объект из блока |
| блок ```` ``` ```` без языка с `{…}` | объект из блока |
| `Sure! {"a": {"b": [1]}} Hope this helps.` | `{"a": {"b": [1]}}` |
| два блока ```` ```json ```` | «В ответе 2 JSON-блока, ожидался один.» |
| ```` ```json ```` + `{"shots": [{"vo": "You are ele` (конец) | «Ответ обрывается на строке 5: JSON-объект не закрыт.» |
| блок, где в строке 5 ответа `"a": 1` без запятой, а в строке 6 — `"b": 2` | «JSON не разобран: строка 6, столбец 3 — ожидалась запятая между элементами.» |
| пусто или пробелы | «Ответ пустой.» |
| только текст | «В ответе нет JSON — ни блока ```json, ни объекта в фигурных скобках.» |
| ```` ```json [ … ] ```` | «Ожидался JSON-объект {…}, а в ответе список.» |

Подсказки (`hint`) говорят, что попросить у чата:
- несколько блоков — прислать JSON одним блоком;
- обрыв — написать «continue», склеить продолжение и вставить целиком или запросить часть поменьше;
- синтаксис — исправить JSON в указанном месте.

Причины синтаксических ошибок переведены таблицей `_REASONS` в `extract.py`. Незнакомое сообщение `json`
показывается как есть, в скобках.

### Ошибка ответа в API

`BridgeAnswerError` из любого обработчика превращается в ответ **422** с телом `BridgeError`:

```json
{
  "message": "План не прошёл проверку: 2 ошибки.",
  "hint": "Попросите чат исправить кадры s027 и s031 и прислать часть целиком.",
  "errors": [
    { "path": "s027.image.prompt", "message": "Стилевой токен «8k» — стиль задаёт канон канала" },
    { "path": "s031.vo", "message": "Пустой текст закадра" }
  ]
}
```

Тексты по-русски, без извинений. `errors[]` — ошибки внутри ответа `{path, message}`, где `path` начинается с id
кадра, если ошибка в кадре. Его заполняет проверка схемой задачи (M4.2). Разбор JSON отдаёт `errors: []`: всё сказано
в `message`. Тип фронта — `BridgeError` из `@/types/bridge`.

## Журнал `bridge_runs`

Каждый обмен — строка. Отсюда экран берёт «Последний прогон» и состояние частей плана.

| Поле | Тип | Описание |
|---|---|---|
| `id` | hex uuid | |
| `task` | `plan \| ideas \| reference` | |
| `channel` | `cursus \| otto` | |
| `episode_id` | string \| null | выпуск; `null` у идей и референса |
| `target_id` | string \| null | о чём обмен, кроме выпуска (референс) |
| `prompt_id`, `prompt_version`, `prompt_hash` | | какой промпт выдан: `RenderedPrompt` |
| `part`, `parts_total` | int ≥ 1 | часть плана; у остальных задач `1/1` |
| `status` | `prompted \| applied \| failed` | промпт выдан / ответ применён / ответ отклонён |
| `errors` | `[{path, message}]` | ошибки отклонённого ответа |
| `created_at`, `answered_at` | ISO 8601 UTC | `answered_at` — `null`, пока ответа нет |

Функции (`runs.py`):

- `open_run(…)` — промпт выдан, строка `prompted`.
- `close_run(id, status, errors)` — ответ принят (`applied`) или отклонён (`failed`). Если обмен уже закрыт
  (повторная вставка после исправления), ответ пишется **новой строкой** с тем же промптом, а закрытая строка не
  меняется: история попыток видна целиком. Неизвестный `id` — `RunNotFound`.
- `record_answer(…)` — ответ без открытого обмена (вставка из старого чата): строка открывается и закрывается сразу,
  `created_at = answered_at`. Промпт — тот, что приложение выдало бы сейчас.
- `latest_runs(episode_id, target_id, task, limit=20)` — новые первыми, фильтры через AND.

**Текст ответа чата в БД не хранится**, хранятся только ошибки. Принятый план ложится файлом версии
`director/vNNN.json` (M4.2), идеи и разбор референса — своими таблицами.

## Источник плана — `plan_source`

`config/providers.yaml → plan_source: bridge | api`, по умолчанию `bridge`. Неизвестное значение — ошибка старта:
«plan_source: «chat» — неизвестный источник плана, допустимо: bridge, api.»

API доступен только с ключом `ANTHROPIC_API_KEY`, и в M4 его нет вовсе: путь через API подключается отдельной
сессией. `plan_source: api` при недоступном API старт не ломает — действует `bridge`, в логе предупреждение.

## API

| Запрос | Ответ |
|---|---|
| `GET /api/bridge/settings` | `BridgeSettings {plan_source, api: {available, reason}}`; `plan_source` — действующий источник |
| `GET /api/bridge/runs?episode_id=&task=&limit=20` | `[BridgeRun]`, новые первыми; `limit` 1…100; неизвестная `task` — 422 |

`api.reason` — подсказка у выключенного сегмента «Claude API» на экране 3:
- без ключа — «Нет ключа ANTHROPIC_API_KEY — docs/api_keys.md»;
- с ключом, пока пути нет, — «Claude API подключается отдельным этапом — пока ответы идут через мост.»

Выдача промпта и приём ответа — у каждой задачи свои: план — раздел «План» ниже, идеи — M4.8, референс — M4.10.

## План

Задача `plan` (M4.2): чат пишет `director.json` частями, приложение подставляет `canon_ref` и `voice`, проверяет и копит
части, а после последней импортирует план версией `vNNN` механизмом M2.4 (`import_plan`, `source: bridge`). Код:
`pipeline/script/plan_bridge.py` (части, контекст промптов, `canon_ref` и `voice`, приём части — чистые функции),
роутер `api/plan.py`, шаблоны `plan_first.md` (часть 1) и `plan_next.md` (часть k).

### Части

- `parts_total = ceil(кадры пресета / plan.shots_per_part)`; размер части — `config/formats.yaml → plan`, 26 кадров:
  Cursus (100) → 4 части, Otto (40) → 2.
- Часть k начинается за последним принятым кадром и берёт `shots_per_part` кадров: `s001…s026`, `s027…s052`, …
  Последняя — до конца плана по пресету. Чат может написать чуть больше или меньше: целостность проверяет сборка.
- Число частей задаёт часть 1: промпты частей 2…N берут `parts_total` из принятой части 1, а не из текущего пресета.
  Ответ на часть 1 начинает новый набор (как ручной импорт M2.4).

### Промпты

| Шаблон | Контекст |
|---|---|
| `plan_first` | `channel_name`, `format`; `preset_json` — минуты, разделы, кадры, темп; `brief_json` — заявка без `idea_id` и `reference_id`; `reference_json` — структура референса, до M4.10 `null`; `meta_json` — `channel`, `episode_id`, `format`, `language`, `target_minutes`, `part`, `parts_total`; `part`, `parts_total`, `first_shot`, `last_shot` |
| `plan_next` | `channel_name`, `format`, `brief_json`; `accepted_json` — конспект принятых частей: `parts_received`, `shots_so_far`, `last_shot {id, section, vo}`, `sections`, id эпох `periods` и обликов `appearances`; `meta_json` — то же плюс `working_title` части 1; `part`, `parts_total`, `first_shot`, `last_shot` |

Правила в тексте промптов:
- ровно один блок ```` ```json ````, `meta` — как дано;
- без `canon_ref` и `voice`, в частях 2…N — ещё без `brief`, `thumbnail` и `publish`: их берёт код из части 1;
- `image.prompt` — только действие, композиция и ракурс; категории стоп-листа перечислены словами;
- формат id: эпоха `caribbean-1716`, облик `<персонаж>@<облик>`; в части k — id из конспекта для тех же эпох и обликов;
- раздел, который переходит в следующую часть, повторяется там без изменений (сборка M2.4 дедуплицирует по `id`);
- `facts[]` со статусом, `source_url` и `shot_id`, проверка веб-поиском.

Конспект в части k нужен, чтобы продолжить мог и новый чат. Эталоны рендера — `tests/fixtures/prompts/plan_first_c01.txt`
и `plan_next_c01_p2.txt`, первая строка — `prompt: <id>, version: <n>`. Текст изменился, а `version` нет — тест
падает. Обновить эталоны: `STUDIO_UPDATE_GOLDEN=1 uv run pytest tests/test_plan_bridge.py`.

### Приём ответа

1. **Извлечение** — `extract_json`.
2. **Ожидаемая часть.** Есть открытый (`prompted`) обмен выпуска — строго его часть: пользователь скопировал её
   промпт. Нет — следующая недостающая, замена уже принятой (после ошибки сборки) или часть 1, которая начинает
   набор заново. Часть — это `meta.part`, по содержимому она не угадывается.
3. **Сверка `meta`**: `episode_id` и `channel` — этого выпуска, `part` — ожидаемая, `parts_total` — как в наборе.
4. **Id эпох и обликов** — по формату, иначе из них не построить ссылки на канон.
5. **Подстановка.** Часть 1 получает `canon_ref` из ссылок кадров и `voice` из профиля канала
   (`docs/director_schema.md`). Части 2…N — без них, а `brief`, `thumbnail` и `publish`, если чат их не прислал, —
   из части 1. Присланные чатом `canon_ref` и `voice` заменяются, в ответе — предупреждение.
6. **Проверка** — `validate_director`, все ошибки сразу, `path` — id кадра.
7. **`canon_ref` набора** — по кадрам всех частей: эпохи и облики новой части дописываются в `canon_ref` части 1,
   которую берёт сборка.
8. **Импорт** — `import_plan(…, "bridge")`: часть ложится в набор, а после последней план собирается, проверяется
   целиком и пишется версией. Ошибка сборки — 422 «План не собрался из частей», части остаются: исправленную можно
   прислать одну.
9. **Журнал.** Обмен закрывается `applied` или `failed` с ошибками; ответ без открытого обмена — `record_answer`.

Ошибки шагов 1–6 ничего не пишут на диск.

| Ответ | `message` |
|---|---|
| план другого выпуска | «Это план выпуска «c07-pirate-ship», а открыт выпуск «c01».» |
| часть не по порядку | «Это часть 3, ожидалась часть 2 — скопируйте промпт части 2.» |
| часть 2 до части 1 | «Это часть 2, ожидалась часть 1 — скопируйте промпт части 1.» |
| `parts_total` не тот | «В ответе parts_total = 5, а план делится на 4 части.» |
| стилевой токен в кадре | «Часть 1 не прошла проверку: 1 ошибка.» + `errors: [{path: "s003", message: "кадр s003: в image.prompt стилевой токен «cinematic lighting» (lighting), …"}]` |
| облик не по формату | `errors: [{path: "s002", message: "кадр s002: облик «Powder Monkey» не по формату, ожидалось <персонаж>@<облик>, …"}]` |
| факт на несуществующий кадр (видно при сборке) | «План не собрался из частей: 1 ошибка.» + `errors: [{path: "facts[3]", …}]` |

### API плана

| Запрос | Ответ |
|---|---|
| `POST /api/projects/{id}/plan/prompt?part=k` | `PlanPrompt {text, prompt_id, version, run_id, part, parts_total, first_shot, last_shot}`, обмен `prompted`. Нет заявки (`brief.idea`) — 409; часть k без принятых 1…k−1 — 409; k больше `parts_total` — 422 |
| `POST /api/projects/{id}/plan/answer` `{text}` | `PlanAnswerResult {run_id, part, parts_total, shots_in_part, received, next_part, import_result, warnings}`; `next_part: null` и `import_result` — план собран и импортирован. Неверный ответ — 422 `BridgeError` |

`warnings` — принято, но стоит посмотреть: подменённые `canon_ref` и `voice`, факты без `source_url`. Типы фронта —
`@/types/plan`.

## Идеи

Задача `ideas` (M4.8): промпт `ideas` по каналу — `POST /api/ideas/prompt`, ответ — `POST /api/ideas/answer`.
Обмен привязан к каналу, выпуска у него нет: открытый обмен ищется по `task` и `channel` (`latest_runs(channel=…)`).
Ответ принимается по идее: битая и дубль пропускаются, причины — в `errors` обмена `applied`; ни одной принятой —
422 и `failed`. Контекст промпта, правила дублей и API — `docs/research.md`, «Идеи».

## Почему нет строк расхода

Мост для приложения бесплатен: запрос в чат идёт по подписке пользователя руками, приложение ничего не оплачивает.
Поэтому мост не вызывает `providers/` и `Gateway`, не пишет строк в `cost_ledger` и не проверяет бюджеты. В смете плана
строка — «мост через чат, $0» (M4.6). Тест `test_bridge_writes_no_cost_rows` проверяет и журнал, и что модули
`pipeline/bridge/` не импортируют `anthropic`, `app.cost` и `app.providers.gateway`; то же для `pipeline/script/` —
`test_plan_bridge_has_no_paid_calls`, а полный цикл плана проверяет, что в `cost_ledger` ноль строк. Маршрут `voice`
мост только читает из конфига, чтобы подставить модель голоса, — вызова провайдера нет.
