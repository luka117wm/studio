# Джобы и события SSE

Контракт очереди долгих операций (принцип 7) и потока событий `GET /api/events`. Появился в M2.5.
Код: `backend/app/jobs/` (`queue.py` — очередь, `worker.py` — пул и контекст обработчика, `events.py` — журнал и
SSE), роутер `backend/app/api/jobs.py`, миграции `storage/migrations/002_jobs.sql`, `003_cost.sql` (M2.6: оценка
платных джобов). Платные вызовы и бюджеты — `docs/providers.md`.

Очередь живёт только в SQLite: процесс можно убить в любой момент, после запуска всё продолжится. Celery, Redis,
очереди в памяти и WebSocket не используются: прогресс идёт в одну сторону.

## Статусы

```
queued ──claim──▶ running ──▶ done | failed | cancelled
   ▲                 │
   └─────────────────┘  перезапуск после аварии; штатная остановка бэкенда
queued ──cancel──▶ cancelled
```

Каждый переход — условный `UPDATE … WHERE status = <ожидаемый>` и строка в `job_events` в одной транзакции.
Опоздавший воркер не затрёт чужой статус, а журнал событий не разойдётся со строкой джоба.

## Поля джоба (`GET /api/jobs/{id}`)

| Поле | Что это |
|---|---|
| `id` | uuid4 hex |
| `kind` | тип обработчика, например `sleep_job` |
| `status` | `queued` · `running` · `done` · `failed` · `cancelled` |
| `progress`, `message` | 0…1 и строка для интерфейса; при отмене и сбое сохраняются как были |
| `payload` | вход, нормализован Pydantic-моделью обработчика (значения по умолчанию подставлены) |
| `result` | `dict` или `null`; при отмене — то, что обработчик успел вернуть |
| `error` | `"<ТипОшибки>: <текст>"`, до 2000 знаков |
| `attempts` | сколько раз обработчик запускался: старты и ретраи; аварийный перезапуск не обнуляет |
| `cancel_requested` | флаг отмены для `running` |
| `episode_id`, `batch_id` | выпуск (FK на `episodes`) и пачка |
| `idempotency_key` | уникален во всей таблице; `null` — без дедупликации |
| `created_at`, `started_at`, `finished_at` | ISO 8601 UTC, до секунды |
| `cost_usd_micro`, `cost_stage` | платный джоб (M2.6): оценка при постановке и её этап; пока джоб `queued`, оценка занимает бюджет; у бесплатных — `null` |

Колонка `jobs.channel` (M5.4, миграция `010`) — канал джоба **без выпуска** (джобы опорных, ниже): по ней его оценка
в очереди занимает месячный бюджет канала. У джоба выпуска она пустая — канал берётся у выпуска. С M5.7 поле
`channel` есть в джобе и в событии SSE: по нему экран канона находит джоб своего канала в общем потоке.

## API

| Запрос | Ответ |
|---|---|
| `POST /api/jobs` `{kind, payload, idempotency_key?, episode_id?, batch_id?}` | 201 — новый джоб; 200 — джоб с этим ключом уже есть, возвращается он (в любом статусе); 422 — неизвестный `kind`, невалидный `payload`, платный джоб без `episode_id`; 404 — нет выпуска; 409 — платный джоб не влезает в бюджет, джоб не создан (тело — `docs/providers.md`, «Бюджеты») |
| `GET /api/jobs?batch=&episode=&status=&kind=&limit=200` | `{items, summary, last_event_id}`: последние `limit` джобов по фильтру в порядке постановки, `summary` — счётчики по статусам по всему фильтру (сводка пачки), `last_event_id` — курсор журнала для подписки |
| `GET /api/jobs/{id}` | джоб или 404 |
| `POST /api/jobs/{id}/cancel` | `queued` → `cancelled` сразу, затем `HandlerSpec.on_cancel` вида, если он есть (ниже); `running` → флаг, ответ со `status: running, cancel_requested: true`; повтор для `cancelled` — 200; `done`/`failed` — 409 |
| `GET /api/events` | поток SSE, ниже |

Пайплайн ставит джобы из Python напрямую: `queue.enqueue` / `queue.enqueue_many` (одна транзакция на пачку), затем
`JobPool.kick()` в потоке event loop.

**Ключ идемпотентности вечный.** Постановка с ключом упавшего или отменённого джоба вернёт его же. Для повтора нужен
новый ключ или отдельная операция «повторить» (её пока нет). Ключ строится из входов, например
`image:<episode>:<shot>:<input_hash>`, тогда повторная постановка того же не создаёт дубль ни до, ни после
перезапуска.

## Обработчик

```python
SPEC = HandlerSpec(kind="sleep_job", fn=sleep_job, payload_model=SleepPayload, resource="cpu")


def sleep_job(ctx: JobContext, payload: SleepPayload) -> dict[str, int]:
    for step in range(1, payload.steps + 1):
        if ctx.cancelled():
            return {"steps_done": step - 1}  # сделанное — в result
        ...
        ctx.progress(step / payload.steps, f"Шаг {step} из {payload.steps}")
    return {"steps_done": payload.steps}
```

- Регистрация — строка в `jobs/handlers/__init__.py → builtin_handlers()`. `create_app(handlers=…)` принимает свой
  набор (тесты).
- `fn` синхронная (идёт в пул потоков, размер = `job_workers`) или `async` (выполняется в event loop). Возвращает
  `dict` или `None`.
- **Идемпотентность.** После аварии джоб перезапускается с начала. Уже оплаченное обработчик пропускает по кэшу
  входов (принцип 8), а не по прогрессу.
- `ctx.progress(fraction, message)` пишет в БД и SSE не чаще раза в 200 мс. Последнее значение не теряется: его
  записывает конечный переход. `fraction = 1.0` пишется всегда.
- `ctx.cancelled()` возвращает `True`, если пользователь отменил джоб (флаг в БД, проверка не чаще раза в 100 мс) или
  бэкенд останавливается. Проверять между шагами, при `True` — вернуть сделанное. Если обработчик закончил работу, не
  заметив отмены, джоб получает статус `done`.
- `ctx.attempt` — номер текущей попытки с учётом прошлых стартов.
- В БД обработчик сам не пишет: переходы статусов делает только пул.
- `max_parallel` (M6.3) — лимит одновременных джобов вида. Пул считает идущие джобы вида и, пока их столько,
  не берёт его `queued` — берёт другие виды; общий пул (`job_workers`) не растёт и не делится на отдельные пулы. У
  `shot_image` — `images_parallel`. Конец джоба вида будит воркеры.
- `on_finish(paths, job)` (M6.3) — после конечного перехода джоба воркером (`done`, `failed`, `cancelled`), в потоке
  loop: пересчитать то, что зависит от итога (статус выпуска). Сбой колбэка — в лог, на джоб не влияет. Пул без
  шлюза (тесты очереди) колбэки не зовёт.
- `on_cancel(paths, job)` (M6.2) — для вида, который при постановке что-то помечает вне очереди (кадр `queued` в
  project.json). Отменённый до старта джоб обработчик не увидит, поэтому пометку снимает этот колбэк — его зовёт
  `POST /api/jobs/{id}/cancel`, когда отмена перевела `queued` в `cancelled`. Запущенный джоб видит отмену в
  `ctx.cancelled()` и снимает пометку сам.

**Платный обработчик** (M2.6) объявляет оценку и ходит к провайдеру только через `ctx.gateway`:

```python
SPEC = HandlerSpec(
    "image_job",
    image_job,
    ImagePayload,
    resource="cpu",
    estimate=lambda gateway, p: gateway.estimate("images", request_of(p)),
)


async def image_job(ctx: JobContext, payload: ImagePayload) -> dict[str, Any]:
    call = CallContext(
        stage="images", episode_id=ctx.episode_id, shot_id=payload.shot_id, job_id=ctx.job_id
    )
    # cached | charged, иначе исключение
    outcome = await ctx.gateway.call(call, request_of(payload))
    return {"status": outcome.status, "path": str(outcome.asset_path)}
```

- `estimate(gateway, payload) -> Cost` — без сети; по ней `POST /api/jobs` проверяет бюджет до постановки и пишет
  `cost_usd_micro`. Платный джоб ставится только с `episode_id`: бюджет считается по выпуску и его каналу.
- `gateway.call` — async, поэтому обработчик платного вызова тоже `async`. Отказ по бюджету в момент вызова (лимит
  заняли, пока джоб ждал) — `BudgetExceeded`, джоб `failed` без повтора.

## Джобы опорных (M5.4)

Лист опорных портретов облика и кадры стиля — платные джобы **уровня канала**: без `episode_id`, с `jobs.channel`.
Ставит их API канона (`POST /api/canon/{channel}/appearances/{id}/anchors`, `…/anchors/{angle}/regenerate`,
`…/anchors/stale`, `POST …/style/anchors` — `docs/canon_schema.md`), а не `POST /api/jobs`: тот отказывает платному джобу без выпуска
(422). Код — `jobs/handlers/anchors.py`, заказ и набор — `pipeline/canon/anchors.py`.

| `kind` | Что рисует | Кандидатов |
|---|---|---|
| `anchor_sheet` | лист облика: сначала фасы без референсов, затем 5 ракурсов с фасом-референсом | 6 × 2 = 12 |
| `anchor_angle` | новые кандидаты одного ракурса или всех устаревших (`…/anchors/stale`, M5.9); номера — следующие за последним | 2 на ракурс |
| `style_anchors` | кадры стиля по шаблонам `config/canon.yaml` в выбранной эпохе, выбор — сразу | 6 |

- **Payload — заказ целиком** (`AnchorOrder`): канал, набор (`target` — облик или `style`), версия, ссылки на версии
  канона и по кандидату: `key`, ракурс, номер, готовый промпт, negative, seed, соотношение сторон, нужен ли фас.
  Его собирает код из опубликованных версий при постановке. Перезапуск после аварии рисует то же самое: оплаченное —
  из кэша по хэшу входов за $0, у `anchor_angle` номера новых кандидатов не сдвигаются.
- **Деньги** — до постановки: оценка `стоимость кандидата × число кандидатов` сверху (кэш не вычитается),
  `Gateway.check_budget(channel=…)` — только месячный бюджет; превышение — 409 с телом `BudgetRefusal`, джоб не
  создаётся. В момент вызова шлюз проверяет бюджет снова. Строки `cost_ledger` — этап `anchors`, без выпуска, с
  `job_id`.
- **Один набор — один джоб.** Пока джоб опорных того же набора `queued` или `running`, второй — 409 «Лист … уже
  собирается (джоб …) — дождитесь окончания или отмените его.»
- **Фас-референс** ищется перед каждым кандидатом с фасом: выбранный фас, если с его версии не менялись лицо,
  телосложение, волосы и возраст (M5.9), иначе первый удавшийся по времени фас версии заказа. Фаса нет — кандидат
  `failed` («нет фаса для референса…») без вызова.
- **Сбой кандидата** — отказ модели или ошибка запроса (`ProviderError`, `RouteError`): кандидат `failed` в
  `sheet.json`, остальные идут (принцип 7). Сеть и 5xx (`TransientError`) — повтор джоба целиком по правилам ниже.
  `BudgetExceeded` — джоб `failed`. Все кандидаты не удались — джоб `failed` с ошибкой первого сбоя.
- **Прогресс** — по кандидатам: «Кандидат 3 из 12 · Три четверти, 1», в конце «Готово 12 из 12: сбоев 0». Отмена —
  между кандидатами; сделанное остаётся в наборе.
- `result`: `{target, done, charged, cached, failed, spent_usd_micro}`.

## Джоб кадра (M6.2)

`shot_image` — одна картинка кадра выпуска, один вариант: платный джоб выпуска (`episode_id`, оценка этапа `images`).
Ставит его `POST /api/projects/{id}/shots/{shot_id}/generate {model?}` (пачка — M6.3), а не `POST /api/jobs`: заказ
собирается кодом при постановке. Код — `pipeline/images/shot_job.py`, спека — `jobs/handlers/shots.py`; контракт
целиком — `docs/generation.md`, «Джоб кадра».

- **Payload — заказ целиком** (`ShotOrder`): выпуск, канал, кадр, вариант, ключ и ID модели, хэш входов и
  `ImageRequest` от сборщика M5.5 (промпт, negative, референсы, seed). Перезапуск после аварии рисует то же.
- **До очереди**: план утверждён, кадр в действующем плане, у сборщика нет проблем, модель из каталога, у кадра нет
  незаконченного джоба `shot_image` (ни отдельного, ни в пачке), бюджет выпуска и месяца. Пачка (M6.3) ставит те же
  заказы своим путём — суммой, одной транзакцией (выше). Отказ — 409 (`ShotRefusal` или `BudgetRefusal`), 404,
  422, джоб не создаётся. Ключа идемпотентности нет: повтор того же заказа после `done` ставит новый джоб, и тот
  находит готовую версию с тем же хэшем без вызова. Перерисовка (`…/redraw`, M6.4) — следующим вариантом и при
  незаконченном джобе кадра: варианты разные, проверки «кадр занят» у неё нет.
- **Статус кадра** в project.json: постановка — `queued`, старт — `generating`, итог — по версии (`done`, `stale`),
  сбой — `failed` с причиной в `ShotState.error`. Отмена до старта — `on_cancel` возвращает кадру прежний статус.
- **Лимит вида** — `max_parallel = images_parallel` (M6.3). **Конец джоба** — `on_finish` пересчитывает статус
  выпуска (`docs/episodes.md`, «Стадия и статус»).
- **Версия плана** заказа (`plan_version`, M6.3): новая текущая версия плана отменяет `queued` джобы кадров выпуска
  (импорт, перевод канона — план снят с утверждения, принцип 10); джоб, который уже рисовал, доделывает, но его
  версия кадра сама не выбирается — нарисована по прежнему плану.
- **Ошибки**: `ProviderError` (отказ фильтра, 4xx), `RouteError` (референс изменился), `BudgetExceeded` в момент
  вызова — кадр `failed`, джоб `failed` без повтора. `TransientError` и сеть — кадр `failed` с текстом, очередь
  повторяет по правилам ниже, попытка снова ставит `generating`.
- **Прогресс** — «Кадр s047 · рисуется», у кадра с персонажами — «Кадр s047 · проверка лица», в конце «Кадр s047 ·
  готово: версия 3» или «Кадр s047 · версия 1 уже нарисована». `result`: `{shot_id, version, status: charged |
  cached | exists | cancelled, usd_micro}`.
- **Проверка лица** (M6.5) — в том же джобе, после файла и до записи версии: результат пишется в `checks.face`
  версии вместе с ней. CPU, ~0.1 с на кадр, веса грузятся один раз на процесс; без весов и при сбое — `skipped`,
  джоб не падает (`docs/generation.md`, «Проверка лица»).
- **Анахронизмы** (M6.6) — после записи версии, прогресс «Кадр s047 · проверка анахронизмов»: вопрос к VLM этапа
  `check` по миниатюре 320, результат — `checks.anachronism` второй записью. Цена вопроса — в оценке джоба
  (`cost_usd_micro` = картинка + вопрос, `cost_stage` — `images`), если вопрос в заказе (`ShotOrder.check`); строки
  журнала — этапа `check`. Выключено в профиле — `off` без вызова; сбой — `failed`, джоб не падает
  (`docs/generation.md`, «Проверка анахронизмов»).

## Перепроверка кадра (M6.5–M6.6)

`shot_check` — проверки выбранной версии кадра заново: лицо (бесплатно, если в кадре есть персонажи) и анахронизмы
(вопрос к VLM, если проверка включена в профиле). Ставит `POST /api/projects/{id}/shots/{shot_id}/check` (201 —
джоб). С вопросом к VLM джоб платный: оценка — `cost_usd_micro` этапа `check`, бюджет выпуска и месяца — до очереди
(409 `BudgetRefusal`); без него — оценки нет. Смета до клика — `GET /api/projects/{id}/check/estimate?shots=` (M6.10,
`docs/generation.md`, «Деньги и выключатель»): та же оценка по каждому кадру. Код — `pipeline/checks/shot_check.py`,
спека — `jobs/handlers/shots.py`.

- **Payload** (`ShotCheckOrder`): выпуск, канал, кадр, версия — выбранная на момент постановки, облики кадра
  действующего плана, вопрос об анахронизмах (`check`; нет — выключено).
- **Результат** заменяет проверенные виды у версии под замком project.json, остальные остаются.
  `result`: `{shot_id, version, face: ok | low | no_face | skipped | null, anachronism: ok | suspect | failed | off
  | null}`; прогресс — «Кадр s002 · версия 2 · не похож на фас — посмотрите кадр; анахронизмов не видно».
- **Лимит вида** — `max_parallel = 1`: модель лица одна на процесс, её вызовы и так идут по очереди. **Конец** —
  `on_finish` пересчитывает статус выпуска: `low` или `suspect` у выбранной версии — `warning`.
- Ключа идемпотентности нет: повтор ставит новый джоб, результат тот же.

## Пачка (M6.3)

Пачка — строка `batches` (миграция `012`): выпуск, вид джобов, модель на пачку, создана, `paused`, `cancelled`,
смета суммой, `parallel` (лимит вида при постановке — для оценки времени), `retry_of` («Повторить упавшие»). Джобы
ссылаются на неё через `jobs.batch_id`. Метка `batch_id` из `POST /api/jobs` без строки `batches` (M2.5) — просто
группа: у неё нет флагов и сводки. Код — `jobs/queue.py` (раздел «пачки»), постановка кадров —
`pipeline/images/batch.py` (`docs/generation.md`, «Пачка»).

- **Постановка** — `queue.insert_batch(conn, batch, jobs)` без commit: вызывающий держит `BEGIN IMMEDIATE` вместе с
  проверкой бюджета суммой (L-021). Не влезло — ни строки пачки, ни одного джоба.
- **Пауза** — `paused = 1`: `claim` не берёт `queued` джобы пачки, идущие доделывают. Флаг в БД — пауза переживает
  перезапуск бэкенда. Продолжить — флаг снят, пул разбужен.
- **Отмена** — `cancelled = 1` и `cancelled` всех `queued` пачки одной транзакцией; `running` доделывают («Очередь
  отменена, начатые кадры дорисуются»). Отменённые джобы не удаляются: история пачки нужна экрану. Оценка отменённых
  перестаёт занимать бюджет — их больше нет в очереди.
- **Сводка** `BatchSummary` (`GET /api/batches/{id}`): `jobs` — счётчики по статусам, `finished` — нет `queued` и
  `running`, `estimate` — смета при постановке, `spent` — `charged` журнала по джобам пачки, `eta_s` — осталось:
  средняя длительность готовых × (в очереди + идёт) / `parallel`, `null` — готовых ещё нет, ждать нечего или пачка
  на паузе (время у джобов — до секунды, у быстрых джобов оценка бывает `0`);
  `paused`, `cancelled`, `retry_of`, `model`.

## Ретраи

`tenacity` вокруг вызова обработчика: экспоненциальная задержка `job_retry_wait_s × 2^(n−1)` (1, 2, 4 … с, не больше
30 с), всего не больше `job_max_attempts` = 3 попыток.

| Ошибка | Повтор |
|---|---|
| `TransientError` (своё исключение; провайдеры переводят в него сеть и 5xx своих SDK) | да |
| `RateLimited` (подкласс `TransientError`) и любое исключение со статусом 429 | да, не раньше `Retry-After` |
| `httpx.TransportError` (соединение, таймауты), встроенные `ConnectionError`, `TimeoutError` | да |
| любое исключение с HTTP-статусом 5xx в `status_code` или `response.status_code` | да |
| остальные 4xx, включая `ProviderError` (401 ключ, 402 оплата, 403 права) и `BudgetExceeded` | нет, сразу `failed` |
| всё остальное (ошибки в коде, валидация) | нет |

**429 и `Retry-After`** (M2.6). Пауза перед повтором — `max(экспонента, Retry-After)`, но не больше 60 с: пауза берётся
из `retry_after` исключения (`RateLimited`) или заголовка ответа `Retry-After` в секундах. Дольше 60 с не ждём:
следующая попытка или `failed` с текстом «уменьшите JOB_WORKERS».

**Повторяет только очередь.** Провайдеры сами не повторяют: SDK Anthropic — `max_retries=0`, google-genai —
`HttpRetryOptions(attempts=1)`, httpx без ретраев. Иначе 3 попытки очереди × 3 попытки SDK.

Отменённый или останавливаемый джоб не повторяется. Перед повтором `attempts + 1`, в `message` — «Повтор 2/3 через 2 с: …»
(событие `job.progress`).

## Перезапуск и остановка

- **Старт** (`JobPool.start` в lifespan): все `running` переводятся в `queued`, `attempts` сохраняются (события
  `job.queued`), события старше 24 ч удаляются.
- **Джоб, роняющий бэкенд.** Если при взятии `attempts` > `job_max_attempts`, джоб сразу `failed` с объяснением.
  Отличает аварийный перезапуск от штатного тот же счётчик.
- **Штатная остановка** (Ctrl+C, `--reload`): `ctx.cancelled()` → `True`, джоб возвращается в `queued`, попытка не
  засчитывается. Кто не уложился в 5 с, остаётся `running` и вернётся в очередь при следующем старте.
- **Один процесс.** Пул живёт в процессе uvicorn; `--workers N` запрещён: каждый процесс при старте вернул бы в
  очередь джобы соседа.

## Пауза GPU (принцип 12)

`HandlerSpec.resource`: `cpu` · `gpu` · `render`. Пока выполняется хоть один `render`-джоб или поднят
`JobPool.gpu_paused`, пул не берёт `gpu`-джобы; уже идущие доделывают. Остальные виды идут как обычно.
`job_workers` ≤ 4 — рендер не больше 4 воркеров.

## Поток SSE: `GET /api/events`

Один поток на клиента, в нём все события всех джобов и heartbeat.

```
retry: 3000

id: 42
event: job.progress
data: {"job_id": "…", "kind": "sleep_job", "status": "running", "progress": 0.5, "message": "Шаг 2 из 4", "attempts": 1, "cancel_requested": false, "episode_id": null, "batch_id": null, "channel": null, "error": null}

event: heartbeat
data: {"ts": "2026-09-23T06:24:21+00:00"}
```

| `event` | Когда |
|---|---|
| `job.queued` | постановка; возврат в очередь после перезапуска или остановки |
| `job.started` | воркер взял джоб (`progress` = 0, `attempts` уже увеличен) |
| `job.progress` | `ctx.progress`, повтор после ошибки, флаг отмены у `running` |
| `job.done` · `job.failed` · `job.cancelled` | конечный статус |
| `batch.updated` | M6.3: сводка пачки (`BatchSummary`) — после постановки пачки, каждого перехода её джоба (кроме `job.progress`), паузы, продолжения и отмены; массовая операция — одно событие на пачку |
| `heartbeat` | раз в `sse_heartbeat_s` = 15 с, без `id` — не сдвигает `Last-Event-ID` |

- У `batch.updated` `data` — сводка пачки целиком, `job_id` строки журнала — джоб, чей переход её изменил (у паузы,
  продолжения и отмены — первый джоб пачки). Клиент фронта (`sse.ts`, M6.7) слушает его вместе с `job.*`, курсор
  общий: событие — `BatchEvent`, у `subscribe` — объединение `StreamEvent`.
- `data` — состояние джоба без `payload` и `result`, их отдаёт `GET /api/jobs/{id}`. Состояние в событии полное, так
  что клиент заменяет его целиком; повтор события безвреден. Форма — Pydantic-модель `JobEventData`
  (`jobs/queue.py`), во фронте — сгенерированный тип `@/types/job` (M2.7).
- Клиент во фронте — `frontend/src/api/sse.ts`: `subscribe(onEvent, {lastEventId, onState})`. Если `EventSource`
  закрылся (бэкенд лежал при подключении), клиент открывает новый с `?last_event_id=` последнего события, паузы
  1, 2, 4 … 30 с; повтор события на стыке отбрасывается по `id`.
- **Сторож тишины.** Прокси Vite не обрывает браузеру начатый поток, когда uvicorn умирает: поток «открыт» и молчит
  (L-023). Поэтому клиент считает поток мёртвым, если дольше 35 с (`SILENCE_LIMIT_MS`: два heartbeat и запас) не
  пришло ни heartbeat, ни события, и переподключается. Меняя `sse_heartbeat_s`, поправить и лимит.
- Одна подписка на приложение — `frontend/src/api/live.ts` (M3.3): снимок → поток с курсора, событие заменяет строку
  джоба в кэше запросов; прогресс джоба канала раз в секунду перезапрашивает наборы опорных канала (кандидаты листа
  видны по ходу сборки), конец — канон канала, конец любого джоба — сводки расходов шапки (M5.9); `batch.updated` —
  сводка пачки в кэш как есть, без перезапроса, а переход джоба кадра (`shot_image`, кроме прогресса) раз в секунду
  перезапрашивает project.json выпуска и смету пачки — плитки экрана 4 (M6.7); обрыв потока —
  проверочный перезапрос экрана (лёг бэкенд — экран «Бэкенд недоступен»), поток снова открыт — запросы
  перезапрашиваются, экран ошибки снимается сам.
- `id` — строка таблицы `job_events` (`AUTOINCREMENT`, не переиспользуется), растёт строго. Поэтому догон работает
  и после перезапуска бэкенда.
- **Курсор.** `Last-Event-ID` в заголовке (EventSource шлёт его сам при переподключении) или `?last_event_id=` (первое
  подключение). Заголовок новее и побеждает. Без курсора приходят только новые события.
- **Подписка без пропусков:** `GET /api/jobs` → `last_event_id` → `new EventSource('/api/events?last_event_id=N')`.
  Курсор снимается раньше списка: событие на стыке придёт дважды, но не пропадёт.
- Журнал хранит сутки. Клиент, пропавший дольше, берёт снимок заново.
- Заголовки: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`. Прокси Vite
  (`/api` → `:8000`) пропускает поток без буферизации (проверено `curl -N localhost:5173/api/events`).
- **Uvicorn и открытый поток.** При остановке uvicorn ждёт закрытия всех соединений до шага lifespan shutdown, и
  открытый поток SSE вешает Ctrl+C и `--reload` навсегда. В `run.sh` стоит `--timeout-graceful-shutdown 3` (L-016).
