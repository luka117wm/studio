## Цель
Проект выпуска создаётся на диске, читается и пишется атомарно, состояние переживает аварийное завершение, схема БД накатывается миграциями.

## Создать / изменить
- `backend/app/storage/paths.py` — все пути одной точкой, никаких склеек строк по коду
- `backend/app/storage/atomic.py` — `write_json_atomic`: temp в той же папке → fsync → rename
- `backend/app/storage/db.py` — подключение SQLite, `PRAGMA journal_mode=WAL`, `foreign_keys=ON`

## Что сделать
1. `paths.py`: `channel_dir`, `episode_dir`, `director_version_path`, `media_dir`, `cache_dir`, `exports_dir`. Корень из переменной окружения, по умолчанию `~/studio/data`.
2. `atomic.py` + тест: записать 500 раз в цикле, в случайный момент бросить исключение внутри записи — файл на диске остаётся валидным JSON либо старой, либо новой версии.
3. Миграции: простой раннер по номеру версии в таблице `schema_version`.
4. Модель `project.json`: ассеты с версиями, тайминги кадров, `*_locked`, статусы, ссылка на текущую версию плана.
5. API проектов, PATCH мёрджит частичное обновление.
6. Дебаунс автосохранения делается на фронте (B1), бэкенд просто быстро пишет.

## Критерии приёмки
- [ ] создание выпуска создаёт дерево папок и `project.json`
- [ ] тест на прерванную запись проходит 500 итераций
- [ ] повторный запуск миграций идемпотентен
- [ ] `PATCH /api/projects/{id}` с одним полем не затирает остальные
