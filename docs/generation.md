# Генерация кадров

Контракт модуля M6: картинки кадров выпуска. Появился в M6.1 (версии кадра), джоб кадра — M6.2, пачка — M6.3,
перерисовка — M6.4, проверка лица — M6.5; анахронизмы — M6.6 (устав `docs/tasks/M6.md`, решения 1–7). Код:
`backend/app/pipeline/images/shot_assets.py` (версии и статусы кадра), `pipeline/images/shot_job.py` (заказ и
джоб), `pipeline/images/batch.py` (пачка), `pipeline/images/status.py` (статус выпуска), `pipeline/checks/`
(проверки), роутеры `backend/app/api/shots.py` и `api/batches.py`, пути — `storage/paths.py`, миниатюры —
`storage/thumbs.py` (общие с листами портретов, M5.9). Поля `project.json` — `docs/project_schema.md`, очередь —
`docs/jobs.md`.

## Версии кадра

Каждая отрисовка кадра — **новая версия**: неизменяемый файл, две миниатюры и строка в `project.json → assets{}`.
Версии не удаляются и не перезаписываются (принцип 8): перерисовка добавляет версию, устаревание ставит кадру
`stale`, выбор другой версии меняет только `ShotState.image_version`.

### Файлы

```
data/projects/<канал>/<выпуск>/media/<кадр>/
  v001.png  v002.jpg  v003.png        версии; расширение — по сигнатуре картинки
  thumbs/
    v001-160.webp  v001-320.webp      миниатюры webp, ширина 160 и 320 (принцип 12)
    …
```

- **Расширение** — по MIME картинки, определённому по сигнатуре байтов (`providers.base.image_mime`): `png`, `jpg`,
  `webp`. Формат выбирает модель (L-039). Не PNG, не JPEG и не WEBP — `NotAnImage`, ничего не пишется.
- **Номер** — следующий после последнего и среди файлов `vNNN.*` каталога кадра, и среди строк `assets` кадра.
  Файл без строки в `assets` (сбой между записью файла и `project.json`) свой номер не отдаёт. 1…999.
- **Запись** — `storage/atomic.write_bytes_new`: temp → fsync → link; если файл с этим именем уже есть —
  `FileExistsError`, существующий не тронут (L-003). Версия из файла шлюза (джоб кадра, M6.2) — `link_new`:
  жёсткая ссылка на файл шлюза в `media/images/<кадр>-<хэш16>.<ext>`, второй копии на диске нет; ссылку не сделать
  (другая ФС) — копия. Оба имени неизменяемы.
- **Миниатюры** строятся сразу при добавлении версии (OpenCV, без растягивания узких картинок, цвет sRGB как у
  исходника). Нет файла миниатюры (данные до M6.1, сбой при записи) — строится при первом запросе.
- В `project.json` путь **относительный**, от каталога выпуска: `media/s001/v002.png`. Абсолютных путей там нет;
  файл, чей путь выходит за каталог выпуска, не отдаётся.

### Строка `assets{}`

id — `img-<кадр>-v<N>`, `kind: image`. Поля `Asset` (`docs/project_schema.md`) плюс метаданные отрисовки:

| Поле | Что это |
|---|---|
| `version` | номер версии кадра, 1… |
| `path` | `media/s001/v002.png` |
| `hash` | хэш входов запроса кадра (принцип 8, сборщик M5.5) — по нему джоб кадра (M6.2) ищет готовое |
| `status` | `ok` |
| `model` | ключ каталога `images` (`config/providers.yaml`): `nb2-lite`, `nb2`, `nb-pro`… — версия помнит свою модель |
| `model_id` | ID модели провайдера на момент вызова (M6.2): ключ каталога позже может вести к другой модели |
| `seed` | seed запроса |
| `variant` | номер варианта: 1 — первая отрисовка, перерисовка берёт следующий свободный (M6.4) |
| `usd_micro` | цена версии, микродоллары; из кэша — `0` |
| `created_at` | когда нарисована, ISO 8601 UTC |
| `cached` | взята из кэша без оплаты (L-042: привязывается к кадру так же, как оплаченная) |
| `checks` | проверки консистентности версии: `face` — раздел «Проверка лица» (M6.5); анахронизмы — M6.6 |

### Выбранная версия и статус кадра

- `ShotState.image_version` — выбранная версия: она идёт в монтаж. Поля нет — картинки у кадра нет.
  `image_version` всегда указывает на ассет-картинку этого кадра, иначе `project.json` не проходит проверку.
- **Новая версия выбирается сама**, если у кадра нет картинки или выбранная устарела (`stale`, есть причины в
  `stale_reasons`): новая нарисована по текущему плану и канону (M6.2, решение пользователя — иначе пачка «все
  `stale`» рисовала бы кадр снова). У готового кадра (`done`) новая версия — вариант на выбор: выбирает человек
  («Сравнение версий», M6.9). То же правило — у версии, найденной по хэшу (повтор заказа).
- Выбор версии — кадр `done`, `stale_reasons` и `error` очищаются. Кадр `removed` при добавлении версии (джоб
  закончил после импорта, убравшего кадр) остаётся `removed`, версия записывается.
- **Статусы кадра.** Работа: `queued` (джоб поставлен), `generating` (джоб рисует), `failed` (сбой, причина — в
  `ShotState.error`: одна строка, что случилось и что сделать). Без работы (`settled_status`): убран — `removed`;
  был сбой — `failed`; есть выбранная картинка — `stale`, если есть причины, иначе `done`; нет — `todo`. Новая
  версия снимает `error`. Кадр, убранный из плана, пока джоб ждал или рисовал, остаётся `removed`.

### Кадр без картинки и `stale`

Устаревать может только картинка. Импорт новой версии плана и перевод канона (`merge_into_project`) не делают
`stale` кадр без выбранной картинки: статус остаётся прежним (`todo`), причины, по которым кадр с картинкой стал бы
`stale`, дописываются в `stale_reasons` как история изменения — без повторов; в отчёте импорта у такого кадра
`stale: false`. Первая выбранная версия историю очищает. Ручная правка промпта или крупности (`edit_stale`) — по
тому же признаку: есть выбранная версия. Правила — `docs/director_schema.md`, «Импорт и версии».

### Запись `project.json`

Все «прочитал — поправил — записал» `project.json` — под замком выпуска (`storage/atomic.update_lock`, L-049):
версии и статусы кадра, PATCH, импорт плана (и перевод канона), утверждение. Запись версии идёт из потока
(`asyncio.to_thread` в джобе кадра), API — из цикла событий, а атомарная запись не спасает от потерянного
обновления. Результат проверяется целиком как `Project` и пишется атомарно.

### API

Префикс — `/api/projects/{episode_id}/shots/{shot_id}`. Кадр — из текущей версии плана.

| Метод и путь | Что |
|---|---|
| `POST …/generate {model?}` | заказ кадра — джоб `shot_image` (раздел «Джоб кадра»); 201 — джоб |
| `POST …/redraw {model?, prompt?}` | перерисовка следующим вариантом, «С правкой…» (раздел «Перерисовка и версии»); 201 — джоб |
| `GET …/redraw/estimate?model=` | какой вариант и почём нарисует `redraw` |
| `GET …/images` | `ShotImages`: версии кадра с метаданными, новые сверху, и выбранная |
| `POST …/images/{version}/choose` | выбрать версию; ответ — `ShotImages` |
| `GET …/images/{version}/thumb?w=160\|320` | миниатюра webp, по умолчанию `w=320` |
| `GET …/images/{version}/file` | картинка как есть, тип — по расширению (`image/png`, `image/jpeg`, `image/webp`) |
| `POST …/check` | перепроверка выбранной версии — джоб `shot_check`, бесплатно (раздел «Проверка лица»); 201 — джоб |

Файлы и миниатюры отдаются с `Cache-Control: public, max-age=31536000, immutable`: версия по адресу не меняется.

      "hash": "sha256:9c1e…", "status": "ok", "model": "nb2-lite", "seed": 2814, "variant": 2,
      "usd_micro": 34000, "created_at": "2026-10-22T09:41:07+00:00", "cached": false },
    { "id": "img-s001-v1", "shot_id": "s001", "kind": "image", "version": 1, "path": "media/s001/v001.png",
      "hash": "sha256:51aa…", "status": "ok", "model": "nb2", "seed": 1907, "variant": 1,

Кадр без картинок — `{"shot_id": "s004", "status": "todo", "image_version": null, "versions": []}`.

**Ошибки** — `{"detail": "…"}` по-русски:

| Код | Когда | Текст |
|---|---|---|
| 404 | выпуска нет | «Выпуск «nope» не найден.» |
| 404 | план не импортирован | «План ещё не импортирован — кадров нет. Импортируйте план на экране «Сценарий».» |
| 404 | кадра нет в текущем плане | «Кадра s099 нет в плане v001 — проверьте id кадра.» |
| 404 | кадр убран из плана | «Кадр s006 убран из плана v002 — картинок у него нет.» |
| 404 | у кадра нет такой версии (в том числе версия другого кадра) | «У кадра s001 нет версии 2 — есть 1.» / «У кадра s004 ещё нет картинок — сначала сгенерируйте кадр.» |
| 422 | ширина миниатюры не 160 и не 320 | `detail[0].msg`: «Ширины миниатюры 200 нет — есть 160 и 320.» |

Выбор несуществующей версии `project.json` не меняет.

## Джоб кадра

M6.2 (устав M6, решения 2, 3, 6). Один кадр, один вариант — джоб `shot_image` (`docs/jobs.md`, «Джоб кадра»). Пачка,
пауза и параллельность — раздел «Пачка» (M6.3); «Перерисовать», «Добавить версию», «С правкой…» — раздел
«Перерисовка и версии» (M6.4).

### Заказ — `POST /api/projects/{episode_id}/shots/{shot_id}/generate`

Тело `ShotGenerate {model?}`: ключ каталога `images` или ID модели из него, без поля — профиль качества по умолчанию
(`docs/providers.md`, «Модель кадра»). Вариант — 1. Проверки по порядку, все до траты денег:

1. **План утверждён** (принцип 10): утверждена текущая версия. Иначе 409 `plan_not_approved`.
2. **Кадр в действующем плане** (версия с правками, не `removed`). Иначе 404 «Кадра s999 в действующем плане
   выпуска нет.»
3. **Запрос собран** сборщиком M5.5 (`build_shot_request(…, variant, model)`) без `problems`. Иначе 409
   `shot_problems` со списком проблем и адресатами `canon` — как у предпросмотра и «Утвердить план». Модель не из
   каталога — 422 со списком доступных.
4. **Кадр не занят**: незаконченного джоба `shot_image` у кадра нет. Иначе 409 `shot_busy` с `job_id`.
5. **Бюджет** выпуска и месяца на цену кадра выбранной модели (кэш не вычитается). Иначе 409 `BudgetRefusal`, строка
   `refused` в журнале.

Затем джоб в очередь (оценка держит бюджет, пока он ждёт) и кадр — `queued`. Ответ 201 — джоб.

`ShotRefusal` (тело 409, кроме бюджета):

```json
{"detail": {"code": "shot_problems",
            "message": "Кадр s006 нельзя рисовать: 1 проблема — исправьте и поставьте снова.",
            "problems": [{"message": "кадр s006: у облика bosun@caribbean-1716 нет листа опорных портретов — соберите его на экране «Канон»",
                          "canon": {"kind": "appearance", "id": "bosun@caribbean-1716", "issue": "no_sheet"}}],
            "job_id": null}}
```

| `code` | `message` |
|---|---|
| `plan_not_approved` | «План не утверждён — утвердите его на экране «Сценарий»: кадры рисуются только по утверждённому плану.» / «Утверждена версия v001, а текущая — v002: утвердите план снова на экране «Сценарий».» / «Плана ещё нет — …» |
| `shot_problems` | «Кадр s006 нельзя рисовать: N проблем — исправьте и поставьте снова.», список — в `problems` |
| `shot_busy` | «Кадр s002 уже рисуется (джоб …) — дождитесь окончания или отмените его.», `job_id` — тот джоб |

### Вариант, seed и хэш

Заказ (`ShotOrder`) несёт запрос целиком. **Вариант 1** — тот же запрос, что показал предпросмотр
(`GET …/shots/{id}/prompt`): тот же seed и тот же `input_hash`. **Вариант N ≥ 2** меняет только seed —
`seed_of(выпуск, кадр, ссылки канона…, действие, N)`: промпт, negative и референсы те же, хэш другой. Модель меняет
маршрут, а с ним хэш, лимит референсов и цену. Номер варианта — в payload: перезапуск после аварии рисует тот же
вариант.

### Отрисовка

1. Старт: кадр `generating`, прогресс «Кадр s002 · рисуется». Джоб снят до старта — кадр к прежнему статусу.
2. **Тот же хэш уже среди версий кадра** — та же версия (по правилу выбора выше), без вызова, без денег, без строки
   журнала: `result.status = exists`. Так повтор того же заказа ничего не платит.
3. Иначе **шлюз** (`Gateway.call`, этап `images`, выпуск, кадр, джоб, `override` = модель заказа):
   - `charged` — оплаченный вызов, строка журнала `charged` с `shot_id`;
   - `cached` — хэш есть в кэше шлюза, но не среди версий кадра (строка `assets` потеряна): $0, строка `cached`.
   В обоих случаях файл шлюза становится **новой версией кадра** (L-042): `cached: true` и `usd_micro: 0` у
   `cached`, цена — у `charged`.
4. Конец: «Кадр s002 · готово: версия 3», `result` — `{shot_id, version, status, usd_micro}`.

**Сбой.** Отказ модели (`ProviderError`: фильтр безопасности, 4xx), ошибка запроса (`RouteError`: референс изменился)
и бюджет в момент вызова (`BudgetExceeded`) — кадр `failed`, текст — в `ShotState.error`, джоб `failed` без повтора:
отказ фильтра детерминирован, повтор только тратит деньги. Сеть и 5xx (`TransientError`) — кадр `failed` с текстом,
очередь повторяет (`docs/jobs.md`, «Ретраи»), попытка снова ставит `generating`. Другой модели при отказе нет.
Пример причины: «Gemini не нарисовал картинку (IMAGE_SAFETY) — сработал фильтр безопасности: насилие и опасные
действия — смягчите действие кадра.»

## Пачка

M6.3 (устав M6, решения 4, 5). «Сгенерировать N кадров (~$X)» — одна пачка джобов `shot_image`: смета и бюджет —
суммой до очереди, пачка и джобы — одной транзакцией. Код — `pipeline/images/batch.py`, роутер — `api/batches.py`;
очередь, пауза и события — `docs/jobs.md`, «Пачка».

### Выбор кадров

| Тело `BatchCreate` | Кадры |
|---|---|
| `{}` | кадры действующего плана без выбранной картинки и `stale` — вариант 1 |
| `{shots: [...]}` | названные, по порядку, без повторов — вариант 1 |
| `{redraw: true}` | все кадры плана (или названные) — следующий свободный вариант: после последнего среди версий кадра |
| `{model: "nb2-lite"}` | модель на пачку — ключ каталога `images` или ID модели; нет — профиль по умолчанию; не из каталога — 422 |

Пропускаются с причиной (`skipped[]`: `{shot_id, reason, problems}`): кадра нет в действующем плане, кадр убран, у
сборщика есть `problems` — список с адресатами `canon`, как у заказа одного кадра. Рисовать нечего — 409
`nothing_to_draw`.

### Смета — `GET /api/projects/{id}/generate/estimate?shots=&model=&redraw=`

Те же кадры, что поставит `POST …/generate` с этими полями; `shots` — id через запятую. `BatchEstimate {model,
model_id, count, unit, total, shots: [{shot_id, variant, usd}], skipped}`: `unit` — цена кадра выбранной модели до
десятых цента, `total` — `count × unit`. Кэш не вычитается — оценка сверху, как у листов портретов. Ничего не пишет.

### Постановка — `POST /api/projects/{id}/generate`

1. План утверждён (текущая версия) — иначе 409 `plan_not_approved`.
2. Выбор кадров и заказы (выше): модель — 422, рисовать нечего — 409.
3. `BEGIN IMMEDIATE` (L-021), внутри:
   - кадры не заняты: ни один не в `queued`/`running` джобе кадра — ни в пачке, ни отдельно (M6.2). Иначе 409
     `shots_busy` со списком кадров и `batch_id` пачки, где они заняты (`null` — отдельный джоб);
   - **бюджет суммой**: цена кадра × число кадров против лимитов выпуска и месяца (`Gateway.check_budget`). Не
     влезает — 409 `BudgetRefusal` с суммой пачки в `cost_usd_micro`, строка `refused` в журнале, ни одного джоба;
   - строка пачки и все джобы (`queue.insert_batch`).
4. Кадры — `queued` одной записью project.json, выпуск — `generating`. Ответ 201 `BatchResult {batch, skipped,
   warnings}`.

Две пачки, поставленные одновременно, не пройдут в лимит вдвоём: вторая ждёт `BEGIN IMMEDIATE` первой и видит её
оценки в очереди.

### Пауза, продолжение, отмена

`POST /api/batches/{id}/pause | resume | cancel` → `BatchSummary`; нет пачки — 404 «Пачка «…» не найдена.»

- Пауза: новые джобы пачки не стартуют, начатые дорисовываются; переживает перезапуск бэкенда.
- Отмена: `queued` — `cancelled`, их кадры — к своему статусу (`settled_status`), начатые дорисуются; оценка
  освобождает бюджет. Отменённые джобы остаются в истории пачки (`GET /api/jobs?batch=`).
- Новая текущая версия плана (импорт, перевод канона) отменяет `queued` джобы кадров выпуска сама: план снят с
  утверждения (принцип 10). Уже рисующий джоб доделывает, но его версия сама не выбирается
  (`ShotOrder.plan_version`).

### «Повторить упавшие» — `POST /api/batches/{id}/retry-failed {shots?}`

Новая пачка (`retry_of` — эта) из кадров с упавшим джобом в этой пачке: тот же вариант и модель, запрос собирается
заново по действующему плану — «С правкой…» в него попадает. **Отказ модели** (джоб упал `ProviderError`) **при том
же запросе** повторится наверняка, поэтому без `shots` такой кадр не ставится: он в `skipped` и в `warnings` («Не
повторены s005: модель отказала, а запрос не менялся — …»); если других нет — 409 `nothing_to_draw` с этим текстом.
С `shots` — повторяются названные, отказ тоже. Деньги и занятость — как у постановки.

### Сводка — `GET /api/batches/{id}`

`BatchSummary` — `docs/jobs.md`, «Пачка»: счётчики джобов, готово ли, смета, потрачено, пауза, отмена, оценка
времени. По каждому переходу джоба пачки в поток SSE идёт `batch.updated` с той же сводкой.

### Статус выпуска

`pipeline/images/status.py`, `docs/episodes.md`, «Стадия и статус»: идёт работа над кадрами (пачка, в том числе на
паузе, или отдельный джоб) — `generating`; кончилась — `ready` (у всех кадров плана картинка в силе, `done`) или
`warning` (есть `failed`, `stale` или кадр без картинки). Пересчёт — при постановке, конце каждого джоба кадра
(`on_finish`) и отмене.

## Перерисовка и версии

M6.4 (устав M6, решения 2, 4, 9). «Перерисовать», «Добавить версию» и «С правкой…» — одно действие на бэкенде:
`POST /api/projects/{id}/shots/{shot_id}/redraw {model?, prompt?}` → 201 джоб `shot_image`. Код —
`api/shots.py`, `pipeline/images/shot_job.py → redraw_order, next_variant`.

- **Вариант** — следующий свободный: максимум из вариантов версий кадра и вариантов его `queued`/`running` джобов
  кадра + 1 (`next_variant`). Два «Перерисовать» подряд — варианты 2 и 3 с разными seed и хэшами, а не дважды 2.
  Поэтому перерисовка, в отличие от заказа варианта 1 (`…/generate`) и пачки, ставится и при незаконченном джобе
  того же кадра.
- **Выбор.** Правило новой версии — как у всех (раздел «Выбранная версия и статус кадра»): выбирается сама, если
  картинки нет или выбранная устарела (`stale`); у готового кадра (`done`) новая версия — вариант на выбор, выбирает
  человек («Сравнение версий», M6.9, `POST …/images/{version}/choose`). Решение пользователя 2026-10-22 (E-1): так же,
  как в M6.2, — иначе `stale`-кадр после перерисовки оставался бы со старой картинкой и пачка рисовала бы его снова.
- **«С правкой…»** — `prompt`: новое действие кадра. Порядок такой, чтобы отказ ничего не оставлял на диске:
  1. правка проверяется как PATCH правок кадра (`api/projects.py → patched_project`): `Shot`, `check_shot` —
     стоп-лист стилевых токенов (принцип 13) и непустое действие. Токен — 422 «кадр s002: в image.prompt стилевой
     токен «cinematic lighting» (…)», пустое — 422; `project.json` не меняется, джоба нет;
  2. заказ собирается по поправленному кадру — проблемы сборщика — 409;
  3. бюджет на цену кадра — 409 `BudgetRefusal`;
  4. только затем правка пишется в `user_override.image.prompt` (у кадра с картинкой — ручной `stale` «Промпт изменён
     вручную», `docs/project_schema.md`) и джоб встаёт в очередь. На листе экрана 3 кадр с пометкой правки
     (`overridden: ["image.prompt"]`).
- **Отказ фильтра → «С правкой…».** У `failed` кадра `error` снимает только удачная версия; повторный отказ пишет
  новый текст.
- **Цена до клика** — `GET …/shots/{shot_id}/redraw/estimate?model=` → `RedrawEstimate {shot_id, variant, model,
  model_id, usd}`; тот же вариант, что поставит `redraw` сейчас. Ничего не пишет. Ошибки — как у `redraw`, кроме
  правки.
- **Пачка `redraw: true`** (раздел «Пачка») берёт тот же `next_variant` каждому кадру; сумма — до постановки.
- Версии не удаляются, выбранная не перезаписывается: перерисовка только добавляет версию.

## Проверка лица

M6.5 (устав M6, решение 7). У каждой новой версии кадра с персонажами посчитано, похож ли каждый персонаж на себя:
сходство лица с выбранным фасом его облика. Только пометка — ни генерация, ни утверждение, ни стадия выпуска от неё
не зависят. Код — `pipeline/checks/face.py`, перепроверка — `pipeline/checks/shot_check.py`, настройки —
`config/checks.yaml`.

### Модели и веса

| | Файл | Лицензия | Источник |
|---|---|---|---|
| Детектор YuNet, `cv2.FaceDetectorYN` | `face_detection_yunet_2023mar.onnx` | MIT | [opencv_zoo](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet) |
| Эмбеддинг SFace, `cv2.FaceRecognizerSF` | `face_recognition_sface_2021dec.onnx` | Apache 2.0 | [opencv_zoo](https://github.com/opencv/opencv_zoo/tree/main/models/face_recognition_sface) |

Обе модели работают в `opencv-python-headless` на CPU, без torch. InsightFace, ArcFace и прочие веса с
некоммерческой лицензией не берём (`CLAUDE.md`). Веса в git не кладутся:
`PYTHONPATH=backend uv run python -m app.tools.fetch_models` качает их в `data/models/` с зеркал из
`config/checks.yaml` (opencv_zoo, затем Hugging Face `opencv/…`) и сверяет sha256. Файл на месте с верным хэшем — не
качает; хэш не совпал — качает заново через временный файл, чтобы обрезок не остался под именем весов. Веса
грузятся один раз на процесс, при первой проверке (~0.5 с); появились после старта — подхватываются без
перезапуска.

### Эталон и кадр

- **Эталон облика** — выбранный фас его листа (`chosen.json → front`), тот же файл, что сборщик подаёт первым
  референсом кадра (`prompt_builder.anchor_refs`). На фасе — самое крупное лицо. Эмбеддинг фаса — кэш по sha256
  файла: перевыбранный фас считается заново.
- **Кадр** уменьшается до `detect_max_side` (1280) по большей стороне. Лица — все, что нашёл YuNet с уверенностью не
  ниже `detect_score` и стороной рамки не меньше `min_face_px` (48 px): мельче SFace даёт шум, поэтому на общем плане
  лица часто не проверяются. Каждое лицо выравнивается (`alignCrop`) и превращается в эмбеддинг.
- **Сходство облика** — лучшее косинусное сходство его фаса среди лиц кадра (−1…1). Облики сравниваются
  независимо: два облика могут опереться на одно лицо.

### Статусы

| Облик (`FaceMatch.status`) | Когда |
|---|---|
| `ok` | сходство не ниже порога |
| `low` | ниже порога — пометка `consistency_low` |
| `no_face` | в кадре нет лиц, которые можно проверить |
| `skipped` | нет выбранного фаса, фас не читается, на фасе не найдено лицо — причина в `reason` |

Кадр (`FaceCheck.status`): лиц нет — `no_face` («не проверено», не подозрение: спина, общий план); иначе хоть один
облик `low` — `low`; хоть один `ok` — `ok`; иначе `skipped`. Вся проверка `skipped` с причиной в `reason`, если нет
весов («Нет весов проверки лица (…) — запустите `…fetch_models`»; предупреждение в журнал — один раз на процесс),
веса не совпали по sha256, картинка версии не читается или проверка упала («Сбой проверки лица (…) — перепроверьте
кадр»). Кадр без обликов не проверяется: поля `checks` у версии нет.

### Порог

`threshold` в `config/checks.yaml` — **0.47**, мягкий: пометка — повод посмотреть, сетка «Подозрительные» (M6.10)
всё равно сортирует по сходству. Подобран на своих картинках `tests/fixtures/faces/` (наш Gemini, стиль канала,
2026-10-25): тот же мальчик против своего фаса — 0.53 (профиль)…0.77 (три четверти), кадр в сцене — 0.63; чужой в
кадре — 0.35…0.42. Порог 0.363 из документации SFace подобран для фото: у нарисованных в одном стиле лиц сходство
чужих выше, и с ним не помечалось бы ничего. Известный предел: два фронтальных портрета разных людей на одном фоне и
в одной одежде дают 0.52 — выше порога.

### Где идёт

- **В джобе кадра** (`shot_image`): после файла от шлюза — `charged` или `cached` — и до записи версии; результат
  пишется в `checks.face` вместе с версией, одной записью `project.json`. ~0.1 с на кадр на CPU, первая проверка
  фаса — ещё ~0.3 с. Версия по тому же хэшу (`exists`) не перепроверяется.
- **Перепроверка** — `POST /api/projects/{id}/shots/{shot_id}/check` → 201, джоб `shot_check` (`docs/jobs.md`):
  выбранная версия против фасов обликов кадра действующего плана, например после смены фаса или скачивания весов.
  Результат заменяет `checks.face` версии, другие проверки остаются. Ошибки: кадра нет в плане — 404, как у версий;
  нет картинок — 404 «У кадра s004 ещё нет картинок — сначала сгенерируйте кадр.»; версии есть, но ни одна не
  выбрана — 404 «У кадра s004 не выбрана картинка — выберите версию, потом проверяйте.»; в кадре нет персонажей — 409
  «В кадре s001 нет персонажей — сравнивать лицо не с чем.»
- **Статус выпуска**: `low` у выбранной версии — `warning` (`docs/episodes.md`, «Стадия и статус»).
