## Цель
Долгие операции ставятся в очередь, идут в фоне, переживают перезапуск бэкенда, шлют прогресс в браузер и отменяются.

## Что сделать
1. Статусы: `queued`, `running`, `done`, `failed`, `cancelled`. Поля: тип, payload, idempotency_key (UNIQUE), попытки, ошибка, прогресс 0…1, время.
2. При старте приложения все `running` переводятся в `queued` — значит, был аварийный перезапуск.
3. Идемпотентность: постановка с существующим ключом возвращает существующий job, а не создаёт второй.
4. Воркер: пул из N задач (конфиг), обработчики регистрируются по типу джоба.
5. Ретраи: экспоненциальная задержка, максимум 3 попытки, только для сетевых и 5xx. 4xx не повторяется.
6. Сбой одного элемента пачки не валит пачку: элемент `failed`, остальные идут дальше.
7. Отмена: флаг в БД, обработчик проверяет его между шагами.
8. SSE: один поток на клиента, события `job.progress`, `job.done`, `job.failed`, heartbeat раз в 15 с.
9. Тестовый обработчик `sleep_job` для проверок.

## Критерии приёмки
- [ ] пачка из 10 `sleep_job`, `kill -9` бэкенда на пятом → после рестарта пачка доходит до конца, повторов нет
- [ ] постановка с тем же idempotency_key не создаёт дубль (тест)
- [ ] отмена останавливает джоб не позже чем через шаг
- [ ] SSE отдаёт прогресс, клиент переподключается после обрыва
