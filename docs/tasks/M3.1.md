# M3.1 — Бэкенд выпусков: создание, правка, сводка для карточки

**Модуль:** M3 — Выпуски и календарь слотов · **Оценка:** 4 ч · **Модель:** Opus · **План до кода:** да

## Цель
Выпуск создаётся без ручного id и названия, переименовывается через `PATCH`, а список выпусков отдаёт всё, что
показывает карточка доски: кадры по статусам, длительность, слова VO, расход и текущий джоб.

## Что сделать
1. **Id на сервере.**
   - Без `id` в теле: `{инициал канала}{NN}` — `c01`, `c02`, `o01`. Номер = максимум среди выпусков канала вида
     `^[co]\d+$` плюс один.
   - Гонка двух `POST` исключена: выбор номера и вставка идут в одной транзакции `BEGIN IMMEDIATE`.
   - Явный `id` проверяется как раньше: шаблон, 409 на дубль и на существующий каталог.
2. **Название.** Без `title` — «Новый выпуск». `short_title` — необязательное короткое имя для ячейки слота.
3. **Происхождение и стадия.** `origin` по умолчанию `blank`. Стадия при создании: `reference` и `blank` — `script`,
   `backlog` — `idea`. `backlog` в M3 принимается API, но интерфейс его не шлёт (M4).
4. **`PATCH /api/episodes/{id}`.**
   - Тело: `title` (непустой, до 200 знаков после `strip`), `short_title` (`null` — сбросить).
   - Меняется `updated_at`; ответ — `EpisodeListItem`.
   - Лишние поля (`stage`, `status`, `channel`, `id`) — 422 с текстом, что их менять нельзя.
5. **Сводка карточки** — чистая функция, без запросов к БД внутри:
   - кадры: `shots_total` (без `removed`), `shots_done`, `shots_failed`, `shots_stale`, `shots_generating`;
   - `vo_words` — слова VO текущей версии плана;
   - `duration_s` и `duration_source`: сумма таймингов (`voice`), иначе оценка по словам при 150 слов/мин
     (`estimate`), иначе `target_minutes` плана (`target`), иначе `null`;
   - `spent_usd_micro` — сумма `charged` + `estimated` журнала по выпуску;
   - `job` — последний `running` или `queued` джоб выпуска: `kind`, `progress`, `message`.
6. **Список.** `GET /api/episodes?channel=` — как раньше плюс `summary`; `channel` отсутствует — оба канала (режим
   «Все каналы»). Порядок: `slot_date` по возрастанию, без слота — в конце по `created_at`. План и `project.json`
   читаются по разу на выпуск; журнал и джобы — одним запросом на список.
7. **Контракт** — в документ: смысл стадии и статуса, правило колонки доски словами (формулу пишет фронт в M3.5),
   формат id, происхождение, поля сводки с единицами.
8. **Типы:** `pnpm -C frontend typegen`, `typegen:check` зелёный.

## Критерии приёмки
- [ ] `POST /api/episodes {"channel":"cursus"}` дважды → `c01`, `c02`; параллельные `POST` не дают дубля (тест с
      двумя соединениями)
- [ ] `PATCH` меняет название, 422 на пустое и на запрещённые поля; `updated_at` растёт
- [ ] сводка на фикстуре `director_pirate_10shots.json` с частью `done` и одним `failed` кадром даёт ожидаемые
      числа; без плана — нули и `duration_s: null`
- [ ] `spent_usd_micro` совпадает с суммой строк журнала выпуска (статусы `charged` + `estimated`)
- [ ] `uv run pytest && uv run mypy backend tests` зелёные; `pnpm -C frontend typegen:check` зелёный

## Чего не делать
- не хранить сводку в БД — она вычисляется из `project.json`, плана и журнала при чтении
- не добавлять поля «на будущее» (миниатюра, CTR): появятся в своих модулях
- не менять `stage` / `status` через `PATCH`
