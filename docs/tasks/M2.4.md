# M2.4 — Импорт версии плана: мёрдж по shot.id, stale, locked

**Модуль:** M2 — Бэкенд-фундамент · **Оценка:** 3 ч · **Модель:** Opus · **План до кода:** да

## Цель
Новая версия `director.json` (целиком или частями 1…N) валидируется, сохраняется как неизменяемый файл `director/vNNN.json`,
мёрджится в `project.json` по `shot.id` с пометкой `stale` для изменённых кадров и без затирания ручных правок;
ответ перечисляет, что именно разошлось.

## Что сделать
1. Версии: `director/v001.json`, `v002.json` … — файл пишется один раз атомарно и больше не меняется; повторный импорт
   байт-в-байт того же плана версию не создаёт (хэш содержимого).
2. Части: `part`/`parts_total`; части копятся во временной области, план собирается после последней; `canon_ref` и
   `voice` берутся из части 1; неполный набор — 409 с перечнем недостающих частей.
3. Мёрдж по `shot.id`: новые кадры добавляются со статусом `queued`; удалённые из плана — в `project.json` помечаются
   `removed` (ассеты не удаляются, принцип 8); изменённые — `stale` с причиной; не изменённые — как были.
4. Ручные правки: поля `*_locked` и `user_override` в `project.json` не затираются; если план меняет заблокированное
   поле — кадр `stale` с причиной «план изменил длину, но длина заблокирована».
5. Смена `canon_ref` (версия стиля, периода, облика) — все кадры с этим обликом/периодом `stale`, картинки на месте
   (принцип 14).
6. Ответ импорта: версия, число добавленных / изменённых / удалённых, список `{shot_id, section, change, drawn_at, price}` —
   ровно то, что показывает `ConflictBar` и таблица расхождений (экран 10).
7. Ошибки валидации — списком из M2.2, статус 422; конфликт частей — 409.

## Критерии приёмки
- [ ] импорт v1 → `director/v001.json`, все кадры `queued`; повторный импорт того же файла версию не создаёт
- [ ] импорт v2 → `v002.json`; ровно 2 кадра `stale` с причинами, 1 добавлен, 1 `removed`, заблокированное поле не изменилось
- [ ] импорт частями даёт тот же `project.json`, что и целиком (сравнение структурно)
