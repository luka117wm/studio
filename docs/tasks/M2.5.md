# M2.5 — Очередь джобов и SSE

**Модуль:** M2 — Бэкенд-фундамент · **Оценка:** 4 ч · **Модель:** Opus · **План до кода:** да

## Цель
Долгие операции ставятся в очередь в SQLite, идут в фоне, переживают перезапуск бэкенда, шлют прогресс в браузер по SSE
и отменяются; сбой одного элемента пачки не валит пачку.

## Что сделать
1. Статусы `queued → running → done | failed | cancelled`; поля: тип, payload (JSON), `idempotency_key`, попытки, ошибка,
   прогресс 0…1, `created_at / started_at / finished_at`, `episode_id`, `batch_id`.
2. При старте приложения все `running` → `queued` (аварийный перезапуск), попытки не сбрасываются.
3. Идемпотентность: постановка с существующим ключом возвращает существующий job.
4. Воркер: `asyncio` задачи поверх пула потоков для синхронных обработчиков; обработчик получает `ctx` с
   `progress(fraction, message)` и `cancelled()`.
5. Ретраи: экспоненциальная задержка, максимум 3 попытки, только для сетевых ошибок и 5xx; 4xx не повторяется.
6. Пачки: `batch_id`; сбой элемента → `failed` у элемента, пачка продолжается; сводка пачки по `GET /api/jobs?batch=`.
7. Отмена: флаг в БД; обработчик проверяет между шагами; `cancelled` с сохранением уже сделанного.
8. SSE: один поток на клиента, `Last-Event-ID` для догона после обрыва, heartbeat; события идут и через прокси Vite
   (`/api` → `:8000`) без буферизации — проверить.
9. Пауза GPU-джобов на время рендера (принцип 12) — только флаг и место в коде, без GPU-обработчиков.

## Критерии приёмки
- [ ] пачка из 10 `sleep_job`, `kill -9` бэкенда на пятом → после рестарта пачка доходит до конца, повторов нет
      (сценарий описан в тесте или в `STATUS.md` как ручная проверка)
- [ ] постановка с тем же `idempotency_key` не создаёт дубль
- [ ] отмена останавливает джоб не позже чем через один шаг
- [ ] `curl -N localhost:5173/api/events` через прокси Vite показывает прогресс и heartbeat
- [ ] `uv run pytest tests/test_jobs.py tests/test_sse.py -v` зелёный
